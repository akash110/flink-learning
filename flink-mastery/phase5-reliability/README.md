# Phase 5 — Reliability: Checkpoints, Savepoints, Exactly-Once

Phases 1–4 taught you to build a stateful streaming job. This phase is about keeping that state alive across crashes, deploys, and rescales — the difference between a demo and a production system.

Everything here follows from one fact: **Flink recovers by rewinding to the last checkpoint and replaying.** Duplicates, exactly-once sinks, restart strategies, savepoint portability — all of it is a consequence of that single design choice.

## The seven things that matter most

1. **Barriers flow in-band with records.** That is why backpressure shows up as slow checkpoints.
2. **Never quote "checkpoint duration".** Decompose it: Start Delay / Alignment / Sync / Async — each has a different cause and a different fix.
3. **`setMinPauseBetweenCheckpoints`** is the highest-value knob and the one nobody sets.
4. **State backend and checkpoint storage are separate settings.** RocksDB does not imply S3.
5. **`uid()` on every stateful operator, from the first commit.** Plus `env.getConfig().disableAutoGeneratedUIDs()` and `env.setMaxParallelism(512)`. Three lines that prevent the three most common production disasters.
6. **Exactly-once state ≠ exactly-once delivery.** Records after the last checkpoint *are* reprocessed. Only a transactional or idempotent sink makes that invisible downstream.
7. **Alert on the age of the last successful checkpoint**, not on checkpoint duration. A job with failing checkpoints looks perfectly healthy while its recovery point silently ages.
