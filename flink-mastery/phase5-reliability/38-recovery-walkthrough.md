# 38. Recovery Walkthrough — a hands-on lab

Everything in chapters 32–37, done with your own hands in about 45 minutes. You will watch a counter survive a job being killed, and then survive being rescaled.

Nothing here needs Kafka, S3, or a cluster. A single downloaded Flink distribution and `netcat`.

> **Key idea**
> The moment recovery stops being abstract is the moment you see a counter resume at 7 instead of restarting at 1. Do this once and you will never be confused about checkpoints again.

## Step 1: The job

A word counter that keeps a running total per word in keyed state, forever. Deliberately simple, so the only interesting thing is whether the counter survives.

`src/main/java/com/example/CountingJob.java`:

```java
package com.example;

import org.apache.flink.api.common.functions.OpenContext;
import org.apache.flink.api.common.state.ValueState;
import org.apache.flink.api.common.state.ValueStateDescriptor;
import org.apache.flink.configuration.Configuration;
import org.apache.flink.runtime.state.hashmap.HashMapStateBackend;
import org.apache.flink.streaming.api.datastream.DataStream;
import org.apache.flink.streaming.api.environment.CheckpointConfig;
import org.apache.flink.streaming.api.environment.CheckpointConfig.ExternalizedCheckpointRetention;
import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;
import org.apache.flink.streaming.api.functions.KeyedProcessFunction;
import org.apache.flink.util.Collector;

public class CountingJob {

    public static void main(String[] args) throws Exception {

        StreamExecutionEnvironment env =
                StreamExecutionEnvironment.getExecutionEnvironment();

        // ---- checkpointing ----
        env.enableCheckpointing(5000);                 // every 5s, so the lab is quick

        CheckpointConfig cp = env.getCheckpointConfig();
        cp.setMinPauseBetweenCheckpoints(2000);
        cp.setCheckpointTimeout(60_000);
        cp.setMaxConcurrentCheckpoints(1);
        cp.setTolerableCheckpointFailureNumber(3);

        // THE line that makes this lab possible: keep the checkpoint after cancel
        cp.setExternalizedCheckpointRetention(
                ExternalizedCheckpointRetention.RETAIN_ON_CANCELLATION);

        cp.setCheckpointStorage("file:///tmp/flink-lab/checkpoints");

        env.setStateBackend(new HashMapStateBackend());

        // Fail fast if any operator is missing a uid
        env.getConfig().disableAutoGeneratedUIDs();

        // ---- the pipeline ----
        DataStream<String> lines = env
                .socketTextStream("localhost", 9999)
                .uid("socket-source")
                .name("Socket source");

        lines
                .flatMap((String line, Collector<String> out) -> {
                    for (String w : line.split("\\s+")) {
                        if (!w.isEmpty()) out.collect(w.toLowerCase());
                    }
                })
                .returns(String.class)
                .uid("tokenizer")
                .name("Tokenize")
                .keyBy(w -> w)
                .process(new RunningCount())
                .uid("running-count")
                .name("Running count")
                .print()
                .uid("stdout-sink")
                .name("Print");

        env.execute("counting-job");
    }

    /** Keeps a per-word running total in keyed state, forever. */
    public static class RunningCount
            extends KeyedProcessFunction<String, String, String> {

        private transient ValueState<Long> countState;

        @Override
        public void open(OpenContext ctx) {
            ValueStateDescriptor<Long> d =
                    new ValueStateDescriptor<>("count", Long.class);
            countState = getRuntimeContext().getState(d);
        }

        @Override
        public void processElement(String word, Context ctx, Collector<String> out)
                throws Exception {
            Long current = countState.value();
            long next = (current == null ? 0L : current) + 1L;
            countState.update(next);
            out.collect(word + " -> " + next);
        }
    }
}
```

### Line notes

- `env.enableCheckpointing(5000)` — 5 seconds is far too aggressive for production; here it means you never wait long for a checkpoint to appear.
- `RETAIN_ON_CANCELLATION` — without this, step 5's `flink cancel` deletes every checkpoint and the whole lab collapses. Chapter 33.
- `setCheckpointStorage("file://...")` — fine for a **single-node** local cluster. On a real multi-node cluster this is broken; see chapter 34.
- `disableAutoGeneratedUIDs()` — makes a missing `uid()` a submission error. That's why every operator here has one.
- `.flatMap((String line, Collector<String> out) -> { ... })` — a lambda implementing `FlatMapFunction`. `Collector<String> out` is how you emit **zero or many** outputs, unlike `map` which emits exactly one.
- `.returns(String.class)` — **required after a lambda flatMap.** Java erases generic types at compile time, so Flink cannot see that the output is `String` and throws `The generic type parameters of 'Collector' are missing`. `.returns(...)` tells it explicitly. (Anonymous inner classes don't need this — the type survives in the class file.)
- `private transient ValueState<Long> countState;` — `transient` means "don't serialize this field". Flink ships the function object to TaskManagers by serializing it; state handles are created at runtime, not shipped.
- `open(OpenContext ctx)` — the initialisation hook, called once per subtask before any record. `OpenContext` replaced `Configuration` in Flink 1.19; on 1.18 the signature is `open(Configuration parameters)`.
- `getRuntimeContext().getState(d)` — this is the **only** way to obtain keyed state. It must happen in `open()`, not in the constructor: the runtime context does not exist yet when the object is constructed on the client.
- `countState.value()` returns `null` when the current key has never been seen. Every Flink keyed-state bug ever written is a missing null check here.

## Step 4: Confirm checkpoints are actually happening

Web UI → your job → **Checkpoints** tab → **History**. A new row every ~5 seconds, all "COMPLETED".

Read the columns from chapter 32: End to End Duration will be a few milliseconds, Sync and Async near zero, Alignment zero (tiny state, no backpressure). That's what a healthy checkpoint looks like.

On disk:

```bash
ls -R /tmp/flink-lab/checkpoints/
```

```
/tmp/flink-lab/checkpoints/7a1c9e2f4b8d6a0c3e5f1a9b7d2c4e6f:
chk-31    chk-32    chk-33    taskowned

/tmp/flink-lab/checkpoints/7a1c9e2f4b8d6a0c3e5f1a9b7d2c4e6f/chk-33:
_metadata
```

Note:
- One directory per **job ID**.
- Only a few `chk-N` — older ones are cleaned up (`execution.checkpointing.num-retained`, default 1; you may see just one).
- `_metadata` is the manifest. It is what you point `-s` at.
- No `shared/` here, because `HashMapStateBackend` has no incremental checkpoints. With RocksDB incremental you would see one, holding most of the bytes.

```bash
ls -la /tmp/flink-lab/checkpoints/*/chk-*/

```

17 KB, and it contains the counts *inlined* — the state is smaller than `state.storage.fs.memory-threshold` (20 KB), so it wasn't given its own file. Chapter 34.

## Step 5: Kill the job

Simulating a crash. `cancel` is the closest thing to an abrupt stop that still leaves you a retained checkpoint:

```bash
./bin/flink cancel 7a1c9e2f4b8d6a0c3e5f1a9b7d2c4e6f
```

```
Cancelling job 7a1c9e2f4b8d6a0c3e5f1a9b7d2c4e6f.
Cancelled job 7a1c9e2f4b8d6a0c3e5f1a9b7d2c4e6f.
```

Verify the checkpoint **survived** — this is the whole point of `RETAIN_ON_CANCELLATION`:

```bash
ls -la /tmp/flink-lab/checkpoints/7a1c9e2f4b8d6a0c3e5f1a9b7d2c4e6f/
```

```
drwxr-xr-x  chk-37
drwxr-xr-x  taskowned
```

Note the exact path of the newest `chk-N`. That is what you restore from.

```bash
CHK=$(ls -d /tmp/flink-lab/checkpoints/*/chk-* | sort -V | tail -1)
echo $CHK
# /tmp/flink-lab/checkpoints/7a1c9e2f4b8d6a0c3e5f1a9b7d2c4e6f/chk-37
```

> **Try the control experiment.** Comment out the `setExternalizedCheckpointRetention` line, rebuild, run, cancel — and watch the entire directory vanish. That is the default behaviour, and it is why so many people believe "checkpoints can't be restored from".

## Step 6: Restart from the retained checkpoint

```bash
./bin/flink run \
  -s $CHK \
  -c com.example.CountingJob \
  /path/to/target/counting-job-1.0.jar
```

```
Starting execution of program
Job has been submitted with JobID 3f8b2c1d4e5a6f7b8c9d0e1f2a3b4c5d
```

New job ID — it is a new job, restored from old state.

Now type into Terminal A again:

```
apple
banana
cherry
```

Expected output:

```
apple -> 5      ← NOT 1. Continued from 4.
banana -> 3     ← NOT 1. Continued from 2.
cherry -> 2     ← NOT 1. Continued from 1.
```

**That is the whole chapter in three lines.** The counts continued across a job that no longer exists, on a JVM that was killed, because the state was in `chk-37`.

Confirm the restore actually happened rather than the counts coinciding — Web UI → the new job → **Checkpoints → Overview → Latest Restore**:

```
Restore ID:   37
Restore Time: 2026-08-29 15:42:11
Type:         Checkpoint
Path:         file:/tmp/flink-lab/checkpoints/7a1c.../chk-37
```

If that panel says "None", you did *not* restore — your `-s` path was wrong and the job started from scratch. Always check this panel after a restore; a silent cold start is the failure mode that costs people their state.

## Step 7: The same thing with a savepoint, plus rescaling

Savepoints are the deliberate version, and they let you change parallelism.

**Take a savepoint and stop the job gracefully:**

```bash
JOB=$(./bin/flink list -r | grep counting-job | awk '{print $4}')
echo $JOB

./bin/flink stop --savepointPath /tmp/flink-lab/savepoints $JOB
```

```
Suspending job "3f8b2c1d4e5a6f7b8c9d0e1f2a3b4c5d" with a savepoint.
Savepoint completed. Path: file:/tmp/flink-lab/savepoints/savepoint-3f8b2c-a91f3e7c2d40
```

`stop` rather than `cancel`: it stops the sources, lets everything settle, and takes a final consistent savepoint. Chapter 35.

```bash
SP=/tmp/flink-lab/savepoints/savepoint-3f8b2c-a91f3e7c2d40
ls -la $SP
```

```
-rw-r--r--  _metadata
```

Same shape as a checkpoint, different directory and a different owner: **Flink will never delete this**, whereas checkpoints are rotated.

**Restore with a different parallelism:**

The job was running at parallelism 1. Bring it back at 3:

```bash
./bin/flink run \
  -s $SP \
  -p 3 \
  -c com.example.CountingJob \
  /path/to/target/counting-job-1.0.jar
```

`-p 3` = parallelism 3. Flink redistributes the keyed state across three subtasks by key group.

> **A caveat for this specific lab:** `socketTextStream` is a non-parallel source (parallelism 1 always), and `print()` at parallelism 3 will interleave. The *counting* operator does run at 3 and its state is genuinely redistributed — which is the part that matters.

Type into Terminal A:

```
apple
banana
```

```
apple -> 6      ← continued across a rescale
banana -> 4
```

The `apple` key now lives on a different subtask than it did before, and its count came with it. That is rescaling.

Check the Web UI: the Running Count operator now shows 3 parallel subtasks, and **Latest Restore** shows `Type: Savepoint`.

### How rescaling actually works: key groups

```
MAX PARALLELISM (default: 128 for parallelism ≤ 128) defines KEY GROUPS.
Each key hashes to exactly one key group, permanently:
    keyGroup = murmurHash(key) % maxParallelism

Key groups are then distributed over subtasks:

parallelism 1:   subtask 0 ← key groups 0..127
parallelism 3:   subtask 0 ← key groups 0..42
                 subtask 1 ← key groups 43..85
                 subtask 2 ← key groups 86..127
parallelism 128: subtask N ← key group N          ← the ceiling
```

Rescaling moves **whole key groups** between subtasks. Nothing is re-hashed, so it is fast and correct.

The consequence you must remember: **`maxParallelism` is fixed at the first run and cannot be changed on restore.** It is the hard ceiling on how far you can ever scale this job.

```java
env.setMaxParallelism(512);   // set it ONCE, at the very beginning, deliberately
```

Set it high (512, 1024) on any job you might ever scale up. The cost of a high max parallelism is a small amount of metadata overhead; the cost of a low one is a full state migration.

**Clean up:**

```bash
./bin/flink cancel $(./bin/flink list -r | grep counting-job | awk '{print $4}')
./bin/stop-cluster.sh
```

## Troubleshooting

### `Cannot map checkpoint/savepoint state for operator ... to the new program`

```
java.lang.IllegalStateException: Failed to rollback to checkpoint/savepoint
file:/tmp/flink-lab/savepoints/savepoint-3f8b2c-a91f3e7c2d40.
Cannot map checkpoint/savepoint state for operator 8a4f2b1c9d3e5f7a2b6c8d0e1f3a5b7c
to the new program, because the operator is not available in the new program.
```

**Meaning:** the savepoint has state under an operator ID the new job graph does not contain.

**Cause, in order of likelihood:**

1. You added, removed, or reordered an operator, and the affected operators had **auto-generated UIDs** — which are hashes of the graph structure, so they all changed. (Chapter 35.)
2. You **changed** an existing `uid()` string. Equivalent to deleting the operator.
3. You genuinely removed a stateful operator.

**Fix:**
- Case 1 or 2: put the UIDs back. Revert the change, add explicit `uid()` to everything, take a fresh savepoint, *then* make your change. There is no shortcut.
- Case 3 only: `--allowNonRestoredState`.

```bash
./bin/flink run -s $SP --allowNonRestoredState -c com.example.CountingJob job.jar
```

**Do not reach for that flag first.** In cases 1 and 2 it starts the job successfully and **silently discards your state** — counters go back to zero and nobody notices until the numbers are wrong days later.

Reproduce it deliberately: change `.uid("running-count")` to `.uid("running-count-v2")`, rebuild, restore. Seeing the exception once, on purpose, is worth more than reading about it.

### Max parallelism mismatch

```
java.lang.IllegalStateException: The maximum parallelism (128) with which the latest
checkpoint of the execution job vertex is compatible does not match the current
maximum parallelism (256) of the execution job vertex.
This indicates that the specified maximum parallelism has changed.
```

**Meaning:** max parallelism defines the key-group count, which defines how keys map to state. Changing it invalidates every key's location.

**Cause:** you set or changed `env.setMaxParallelism(...)`, *or* you crossed a threshold where Flink's default changes. The default is derived from parallelism:

```
p ≤ 128         →  maxParallelism = 128
p > 128         →  maxParallelism = min(nextPowerOfTwo(p + p/2), 32768)
```

So going from parallelism 100 to parallelism 200 changes the default max parallelism from 128 to 512, and the restore fails.

**Fix:**
- Pin it explicitly in the job, matching what the savepoint has: `env.setMaxParallelism(128)`.
- The number is recorded in the savepoint metadata; the exception tells you what it expects.
- To *genuinely* change it, you must migrate state through the [State Processor API](https://nightlies.apache.org/flink/flink-docs-stable/docs/libs/state_processor_api/) — read the savepoint, rewrite it with the new max parallelism, restore from the rewritten one. Slow and manual.

**Prevention:** `env.setMaxParallelism(512)` in every job, from the first commit. It costs almost nothing and removes this class of failure permanently.

### `Auto generated UIDs have been disabled but no UID or hash has been assigned to operator`

```
java.lang.IllegalStateException: Auto generated UIDs have been disabled but no UID
or hash has been assigned to operator FlatMap.
```

**Meaning:** exactly what it says — `disableAutoGeneratedUIDs()` is on and one operator has no `uid()`.

**Fix:** add `.uid("...")`. This exception is your friend: it appears at *submission*, on your laptop, instead of six months later during a migration.

Careful with placement:

```java
// ❌ uid() is on print(), not on process() — process has no uid
.process(new RunningCount()).print().uid("stdout-sink")

// ✅ each operator gets its own
.process(new RunningCount()).uid("running-count")
.print().uid("stdout-sink")
```

### The job restored but counts started from zero

Almost always: **it never restored**. Check **Checkpoints → Overview → Latest Restore** in the Web UI. If it says "None", the `-s` path didn't resolve and Flink started clean **without an error**.

Common causes:
- Path typo, or pointing at the job-id directory instead of `chk-N`. The path must be the directory *containing* `_metadata`.
- Missing `file://` scheme where one was needed.
- Restoring from a checkpoint deleted by `num-retained` rotation between your `ls` and your `run`.
- No `RETAIN_ON_CANCELLATION`, so cancel deleted everything.

### `Size of the state is larger than the maximum permitted memory-backed state`

```
java.io.IOException: Size of the state is larger than the maximum permitted memory-backed
state. Size=5245780, maxSize=5242880. Consider using a different checkpoint storage,
like the FileSystemCheckpointStorage.
```

You never configured checkpoint storage, so it defaulted to `JobManagerCheckpointStorage` with its 5 MB cap. Set `cp.setCheckpointStorage("file://...")` or `execution.checkpointing.dir` in the config. Chapter 34.

### Checkpoints stay "IN PROGRESS" forever

- Nothing is flowing — a socket source with no data never advances, and a checkpoint can't complete if a task isn't running records through. Type something into `nc`.
- Or genuine backpressure. Chapter 32's metrics table, then [`../../01-checkpointing-slow.md`].

### `Could not connect to localhost:9999`

Start `nc -lk 9999` **before** submitting the job. `socketTextStream` fails if nothing is listening. If `nc` dies, the source fails and the job restarts in a loop.

## Remember

- `RETAIN_ON_CANCELLATION` is what makes restarting from a checkpoint possible at all.
- `flink run -s <path>` takes **either** a `chk-N` directory or a savepoint directory — the one containing `_metadata`.
- **Always verify Checkpoints → Overview → Latest Restore.** A failed restore starts the job clean *without erroring*.
- `flink stop --savepointPath <dir> <jobId>` for planned shutdowns; `cancel` only when you don't need a clean final snapshot.
- `-p N` on restore rescales. Keyed state moves as whole **key groups**.
- **`maxParallelism` cannot be changed on restore.** Set `env.setMaxParallelism(512)` from day one.
- `uid()` on every operator, plus `disableAutoGeneratedUIDs()`, turns a future migration disaster into a submission-time error.
- `--allowNonRestoredState` is a scalpel, not a hammer. It silently deletes state you may have wanted.
- After a lambda `flatMap`, you need `.returns(...)` — Java's type erasure hides the output type from Flink.
- Keyed state must be obtained in `open()` via `getRuntimeContext().getState(...)`, and `.value()` returns `null` for an unseen key.

**Interview one-liners**

- *"How do you restart a job from a checkpoint?"* → Enable `RETAIN_ON_CANCELLATION`, find the newest `chk-N` directory under the job-id folder in checkpoint storage, and submit with `flink run -s <that path>`. Then verify Latest Restore in the UI, because a bad path starts the job clean without an error.
- *"How do you rescale a stateful job?"* → `flink stop --savepointPath`, then `flink run -s <savepoint> -p <newParallelism>`. Keyed state is redistributed as whole key groups, bounded by max parallelism.
- *"Why can't you change max parallelism?"* → It defines the number of key groups and therefore the key-to-state mapping. Changing it invalidates every key's location; migrating requires the State Processor API. Set it high on day one.
- *"What does 'Cannot map checkpoint/savepoint state for operator X' mean?"* → The snapshot has state under an operator ID absent from the new job graph — almost always because auto-generated UIDs changed when the topology changed.
- *"When is `--allowNonRestoredState` safe?"* → Only when you deliberately removed a stateful operator and can name it. Otherwise it silently discards state you still wanted.
